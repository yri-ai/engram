DESIGN — Temporal Forecasting Kernel

PASS

1. Problem

Engram currently has a temporal graph and an early branch forecasting scaffold, but forecasts are not yet durable, scoreable, leakage-safe belief objects. The next product step is not a generic retrieval or RAG app. It is a forecasting kernel that can reconstruct the evidence Engram knew at a timestamp, produce an auditable probability distribution, preserve the run immutably, and score it after resolution.

2. Design Thesis

Bitemporal graph
  → as-of evidence state
  → forecast question / resolution contract
  → structured forecaster protocol
  → probabilistic forecast run
  → immutable forecast ledger
  → resolution + proper scoring
  → calibration / update learning over time

The core invariant: Given only what Engram knew at timestamp T, assign probabilities to outcomes by horizon H and preserve why.

3. Goals

  • Make forecast questions explicit contracts with outcome spaces and resolution criteria.
  • Make forecast_as_of mandatory for every forecast.
  • Compile evidence dossiers using record-time and valid-time semantics.
  • Store immutable forecast runs with probability distributions and evidence IDs.
  • Support binary and small closed-branch forecasts first.
  • Resolve forecasts and compute proper scores.
  • Track calibration buckets without claiming calibration prematurely.

4. Non-Goals

  • No temporal graph neural network training.
  • No learned calibration layer in the MVP.
  • No open-ended scenario trees in the MVP.
  • No vector-only evidence selection.
  • No autonomous web-search forecaster as the kernel.
  • No generic continuous numeric forecasting across domains.

8. As-Of Evidence Compiler

The compiler is the moat. It must not behave like generic RAG. It reconstructs an as-of evidence state from graph facts/relationships and their provenance.

Filtering invariants

  • recorded_from <= forecast_as_of
  • recorded_to is null OR recorded_to > forecast_as_of
  • source_ingested_at <= forecast_as_of when available
  • derived_fact_record_time <= forecast_as_of
  • resolution evidence must be excluded
  • post-horizon or post-as-of documents are excluded unless explicitly modeled as unknowable-at-forecast-time valid-world evidence

Because Engram distinguishes valid time from record time, a lease valid on Jan 1 but learned Mar 1 is excluded from a Feb 1 forecast.

9. Repository Strategy

MVP should use a simple filesystem-backed JSON repository under .engram/forecasts/ or a configured path. This keeps the first slice low-risk while the graph store remains the source for evidence. Later, forecast runs can move into graph-backed or relational persistence.

Repository invariants:

  • save_question refuses mutation of active questions unless versioning is explicit.
  • save_run refuses overwrite if run ID exists.
  • save_resolution refuses branch names outside the question outcome space.
  • All writes are JSON-serializable Pydantic dumps.

10. Forecast Protocol

The MVP can ship a deterministic baseline protocol that maps branch support/opposition evidence to probabilities, while preserving a seam for a structured LLM protocol.

  1. Compute base priors over branches.
  2. Adjust by evidence support/opposition metadata.
  3. Apply missing-evidence uncertainty penalty.
  4. Softmax normalized branch scores into probabilities.
  5. Validate probability sum and top branch.
  6. Store rationale with cited evidence IDs.

This avoids claiming model skill before the ledger/scoring substrate exists.

14. Risks and Tradeoffs

  • JSON repository is not final persistence. It accelerates MVP but must be abstracted behind a protocol.
  • Existing PR #10 overlaps. Reuse concepts where possible, but do not inherit architecture language that centers RAG or omits as-of kernel invariants.
  • As-of compiler depends on fact metadata quality. Early implementation may require explicit metadata conventions for source timestamps and evidence direction.
  • Calibration reports will have small samples. The UI/CLI must label low-n summaries as provisional.
  • CLI nesting in Typer may require refactor. Keep command surface minimal if current CLI structure resists grouped subcommands.

15. Compiler Data Source Contract

The as-of compiler must be implementable against the current repo. The first implementation should add explicit store/service methods rather than relying on the existing relationship-only point-in-time queries.

Required graph-store/service methods

async def get_facts_as_of(
    tenant_id: str,
    entity_id: str,
    forecast_as_of: datetime,
    fact_key: str | None = None,
    include_superseded: bool = True,
) -> list[Fact]

async def get_relationships_as_of(
    tenant_id: str,
    entity_id: str,
    forecast_as_of: datetime,
    rel_type: RelationshipType | None = None,
    include_superseded: bool = True,
) -> list[Relationship]

async def get_target_evidence_as_of(
    tenant_id: str,
    target_id: str,
    forecast_as_of: datetime,
    structural_family: str | None = None,
    limit: int = 200,
) -> EvidenceDossier

If changing GraphStore broadly is too invasive for the first slice, implement these as service-level methods over the existing MemoryStore internals and fact/relationship APIs, then promote them into GraphStore once tests stabilize.

Target traversal scope

  • MVP scope starts from ForecastQuestion.target_id.
  • Include direct facts for the target entity.
  • Include active/as-of relationships where target is source or target.
  • Include facts attached to directly related entities only when the relationship is known as-of and the fact is known as-of.
  • Do not recurse beyond one hop in MVP unless explicitly configured.

Fact filter

known = fact.recorded_from <= forecast_as_of
still_known = fact.recorded_to is None or fact.recorded_to > forecast_as_of
not_resolution = metadata.resolution_for_question_id is absent or != question_id
not_posthoc = metadata.derived_after is absent or metadata.derived_after <= forecast_as_of
include iff known and still_known and not_resolution and not_posthoc

Relationship filter

known = relationship.recorded_from <= forecast_as_of
still_known = relationship.recorded_to is None or relationship.recorded_to > forecast_as_of
include iff known and still_known

Deterministic ordering and limits

Order dossier items by record_time, then valid_time, then stable ID. Apply limit after mandatory leakage exclusions. Store excluded counts by reason: future_record_time, retracted_before_as_of, resolution_evidence, posthoc_derived, outside_scope, limit.

16. Supersession and Contradiction Rules

Superseded facts are not silently deleted from as-of dossiers. They are packetized according to what was knowable at forecast_as_of.

CaseDossier behaviorPacket status
Fact is active as-of: recorded_from <= as_of, recorded_to is null or > as_of, status=activeInclude as current evidence.current
Fact was superseded after as-of: original fact known at as-of, replacement recorded after as-ofInclude original fact as current-for-that-run; do not include replacement.current_as_of_later_superseded
Fact was superseded before as-of and replacement is known as-ofInclude replacement as current evidence and optionally include old fact as historical contradiction if include_superseded.superseded_before_as_of for old, current for replacement
Fact has recorded_to <= as_ofExclude from current evidence; include only in audit chain if requested.retracted_before_as_of
Relationship has valid_to <= horizon but is still knownInclude with valid-time window; it may be historically relevant but not active at horizon.historical_valid_window

Packet fields must include supersession_status, supersedes_id, superseded_by_id when known, valid_from, valid_to, recorded_from, recorded_to, and contradicts_ids when a deterministic contradiction rule identifies conflict.

17. Resolution Evidence Marker Contract

Resolution evidence and post-hoc derived facts must be identifiable before compiler tests can be meaningful. MVP metadata convention:

metadata = {
  "source_id": "...",
  "source_path": "...",
  "source_ingested_at": "2025-01-01T00:00:00Z",
  "resolution_for_question_id": "optional-question-id",
  "derived_after": "optional-ISO-timestamp",
  "evidence_role": "forecast_evidence|resolution_evidence|posthoc_derived",
  "structural_family": "optional-family",
  "supports_branch": ["optional-branch"],
  "opposes_branch": ["optional-branch"]
}

Compiler exclusion rules: exclude items with evidence_role=resolution_evidence, matching resolution_for_question_id, source_ingested_at > forecast_as_of, or derived_after > forecast_as_of. Count each exclusion reason.

18. Deterministic Forecast Protocol Details

The baseline protocol must be reproducible without hidden conventions.

  • OutcomeBranch.prior is optional; if omitted, use uniform priors.
  • EvidenceItem.supports_branch and opposes_branch are explicit lists derived from metadata or branch rules.
  • Branch raw score: log(prior) + support_weight * supports - oppose_weight * opposes - missing_penalty * missing_required_evidence.
  • Default support_weight=0.7, oppose_weight=0.9, missing_penalty=0.25, temperature=1.0.
  • Softmax raw scores into probabilities.
  • Probability sum tolerance: abs(sum(p)-1) <= 1e-6.
  • top_branch must equal the max-probability branch, tie-broken lexicographically for determinism.
  • Every rationale claim that cites evidence must cite an ID present in ForecastRun.evidence_ids.

20. Design Review Readiness

This revised design is specific enough to review against the build brief and current repo. It intentionally scopes the first implementation to models, deterministic compiler/repository/scoring/protocol, and CLI/service surface without requiring trained models or full document extraction. It now includes an explicit data-source contract, supersession semantics, resolution-evidence marker contract, deterministic protocol details, and verification commands.
